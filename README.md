# Arena Human Preference 140K — Feature Engineering

This repository accompanies the **LM Arena 140K** dataset: a pairwise, human-preference-labeled corpus of large language model (LLM) conversations in the LMArena format (`user_prompt`, `response_a`, `response_b`, `winner`, `conv_metadata`, `category_tag`). It does not redistribute a scoring model or a single monolithic script — it is a **modular data-processing pipeline** that turns the raw conversation triples into an interpretable, ML-ready feature table, plus an independent LLM-based correctness annotator, built to support downstream work on pairwise preference modeling, reward modeling, and LLM behavioral analysis.

The codebase was developed to produce the auxiliary feature set and annotations released alongside the dataset on Kaggle / Hugging Face. It is published so that the derived columns are reproducible and auditable: every feature has a traceable definition, a pure-function implementation, and a documented fallback behavior for missing or malformed input — there is no hidden preprocessing between the raw dataset and the released feature table.

---

## Why this exists

Pairwise LLM preference datasets (LMArena, Chatbot Arena, and derivatives) ship the raw conversation text and a human preference label, but rarely the structural and behavioral signals that are known to correlate with — and confound — human preference: response length, formatting richness, refusal/truncation failures, language mismatch, instruction-following compliance, and so on. Modeling directly on raw text requires either an expensive transformer pass or accepting these confounds as unmeasured noise.

This repository closes that gap with two complementary, independently usable subsystems:

1. **A dependency-light, regex/heuristic feature extraction pipeline** (`Feature_Extraction/`) that computes several hundred interpretable scalar features per conversation — from both the dataset's own metadata and the raw response text — without invoking any transformer model.
2. **An LLM-as-a-judge correctness annotator** (`LLM_as_a_Judge/`) that independently scores the objective correctness of `response_a` and `response_b` using an external LLM (OpenAI API), under a strict order-invariant, non-comparative protocol — producing a correctness signal that is deliberately *decoupled* from human preference, rather than a second preference vote.

A third module, **language identification** (`Language_Detection/`), underlies both of the above and is documented separately because it is reusable as a standalone utility.

Together they let a researcher regenerate the full derived feature table from the raw CSV in a few function calls, or take any single extractor (e.g. `has_refusal`, `interaction_score`, `format_richness_diff`) and reuse it in isolation.

## Data Model

### Raw input columns (upstream, LMArena-style)

| Column | Type | Description |
|---|---|---|
| `id` | `str` | Row identifier |
| `user_prompt` | `str` | The user's message to both models |
| `response_a` | `str` | Response generated by model A |
| `response_b` | `str` | Response generated by model B |
| `winner` | `str` | Human-annotated pairwise preference label: `model_a`, `model_b`, `tie`, or `both_bad` |
| `conv_metadata` | `dict`-like | Dataset-native structural metadata (bold/list/header counts, token counts, turn count) per response |
| `category_tag` | `dict`-like | Dataset-native, versioned interaction-type labels for the prompt (complexity, creativity, domain knowledge, instruction-following score, etc.) |

`winner` is preserved as-is; nothing in this repository computes or infers it. Every module here derives **auxiliary, explanatory columns** — it never touches the preference label itself, which keeps the engineered features usable as unbiased predictors in downstream modeling rather than leaking target information.

### Derived output columns (this repository)

Running the full pipeline (`Feature_Extraction.Feature_Runners.Run_All_Features.run_all_features`) augments the raw table with four families of columns, distinguished by prefix:

| Prefix | Source stage | Meaning |
|---|---|---|
| `prompt_` | Text Features | Property of `user_prompt` (language, structure, requested format/length, etc.) |
| `a_` / `b_` | Text Features | Same property computed independently for `response_a` / `response_b` |
| `dataset_a_` / `dataset_b_` | Metadata Features | Dataset-native formatting/token fields, mirrored as-is from `conv_metadata` |
| `cat_` | Metadata Features | Flattened, version-tolerant labels from `category_tag` |
| *(no prefix)* | Comparison Features | Pairwise A-vs-B relationship (`{metric}_diff`, `{metric}_ratio`, `{metric}_a_gt_b`, `both_*`/`only_one_*`/`neither_*`) |
| *(unprefixed, custom)* | Metadata Features | Conversation-level scalars not tied to a single response (`turns`, `is_multi_turn`, `turn_density`) |

Separately, `LLM_as_a_Judge` produces its own result table (joinable on `id`) with `prompt_type`, `educational_field`, `correctness_applicable`, and independent per-response correctness verdicts — see [below](#llm-as-a-judge-correctness-annotation).

## Module 1 — Feature Extraction (`Feature_Extraction/`)

A four-layer, dependency-light system (Python stdlib + pandas; `mediapipe` only for language ID) that extracts structural, linguistic, formatting, and quality/failure signals from conversational data, then derives pairwise comparison features from them.

```
┌──────────────────────────────────────────────────────────────────┐
│                        Feature_Runners                           │
│      Batch processing, column-gating, feature merging            │
├───────────────────┬───────────────────┬──────────────────────────┤
│ Metadata_Features │   Text_Features   │   Comparison_Features    │
│ (conv_metadata,   │ (prompt + response│ (a_* vs b_* outputs of   │
│  category_tag)    │  texts)           │  the two stages at left) │
├───────────────────┴───────────────────┴──────────────────────────┤
│                   Individual Feature Extractors                  │
│           Stateless functions operating on single input          │
└──────────────────────────────────────────────────────────────────┘
```

**Metadata Features** (`Metadata_Features/`) read the dataset's own `conv_metadata`/`category_tag` fields and expose them as interpretable scalars: bold/header/list usage, token allocation across turns, conversational turn dynamics, and flattened `cat_*` interaction-type labels (math, creative writing, instruction-following score, etc.). No text is parsed at this stage.

**Text Features** (`Text_Features/`) apply ~25 regex/heuristic extractors directly to raw text — the same extractor set runs independently over `user_prompt`, `response_a`, and `response_b`. Categories include language/script identification, structural statistics (sentence/paragraph counts and dispersion), code/LaTeX/JSON/table detection, lexical repetition, discourse markers (conclusions, next-steps, trailing questions), and quality/failure heuristics (refusal, near-empty, truncation). Two extractors are prompt-only, since they characterize what the prompt *requested* (list/table/JSON/code output; brief/detailed length) rather than a text's own properties.

**Comparison Features** (`Comparison_Features/`) are a second-stage layer: ~30 comparators consume the already-computed `a_*`/`b_*` (and select `dataset_*`) scalar outputs — never raw text — and emit either numeric contrasts (`{metric}_diff`, `{metric}_ratio`, `{metric}_a_gt_b`) or boolean agreement flags (`both_*`, `only_one_*`, `neither_*`), plus a handful of custom composites (format richness, prompt-language/script match, format/length-request compliance).

**Feature Runners** (`Feature_Runners/`) orchestrate all of the above with column-gated execution: each stage — and each individual comparator — checks its required input columns before running, so partial pipelines (e.g. metadata-only, or a dataset missing `category_tag`) degrade to a reduced but valid schema instead of raising.

```python
from Feature_Extraction.Feature_Runners.Run_All_Features import run_all_features

df = run_all_features(df)
```

Full architectural rationale, the complete field-by-field schema, and per-module usage examples are in [`Feature_Extraction/README.md`](Feature_Extraction/README.md) and its four submodule READMEs ([Metadata_Features](Feature_Extraction/Metadata_Features/README.md), [Text_Features](Feature_Extraction/Text_Features/README.md), [Comparison_Features](Feature_Extraction/Comparison_Features/README.md), [Feature_Runners](Feature_Extraction/Feature_Runners/README.md)).

## Module 2 — LLM-as-a-Judge Correctness Annotation (`LLM_as_a_Judge/`)

A separate, optional annotation pipeline that calls an external LLM (default: `gpt-4.1-mini` via the OpenAI API) to independently assess the **objective correctness** of each response — distinct in kind from the human `winner` preference label, and distinct from a conventional pairwise judge.

The evaluation protocol is deliberately constrained to avoid the comparative bias inherent to typical LLM-judge setups:

- `response_a` and `response_b` are scored **independently**, "as if the other response did not exist."
- The judge never selects a winner, ranks the two responses, or is told model identities.
- The prompt is required to be **order-invariant**: swapping A and B must not change either verdict.
- Each response first receives a `prompt_type` classification (educational, chitchatting, code, translation, reasoning, creative writing, etc.), and — if applicable — an `educational_field` label, before a `correctness_level` (`fully_correct` / `partially_correct` / `incorrect` / `unknown`) is assigned only where correctness is objectively defined (math, code, factual, translation, logical, or verifiably-constrained prompts); subjective/creative/open-ended prompts are marked `correctness_applicable: false` and left unscored rather than forced into a spurious verdict.

This produces a correctness signal that can be studied *against* human preference (e.g., "how often does the human-preferred response contain a factual error the loser doesn't?") rather than a signal that simply reproduces it.

```bash
python -m LLM_as_a_Judge.batch_runner \
  --input path/to/lm_arena_140k.csv \
  --output-jsonl judge_results.jsonl \
  --output-csv judge_results.csv
```

Requires `OPENAI_API_KEY` to be set in the environment (see [`LLM_as_a_Judge/README.md`](LLM_as_a_Judge/README.md) for installation, CLI flags, and the full output schema). This module makes external network/API calls and incurs API cost; it is not part of the dependency-light `Feature_Extraction` pipeline and can be skipped entirely without affecting it.

## Module 3 — Language Detection (`Language_Detection/`)

A standalone wrapper around Google MediaPipe's on-device `LanguageDetector` (TFLite), purpose-built for noisy LLM conversation text rather than clean prose. It underlies the `primary_language`/`is_multilingual`/language-match features computed by `Text_Features` and `Comparison_Features`, but is independently importable.

Two entry points:

```python
from Language_Detection import detectLanguage, detectMultiLanguage

detectLanguage("Hello, how are you?")   # -> "en"

detectMultiLanguage(
    "Hello world. C'est un texte mélangé. Как дела?",
    chunk_size=20, min_lang_ratio=0.05,
)
# -> {"is_multi_language": True, "languages": ["en", "fr", "ru"], ...}
```

Before inference, text is cleaned of code fences, LaTeX, URLs, and unfenced code lines (`text_cleaning.py`), since these are common in LLM output and would otherwise be misdetected as language content. Multi-language detection uses CJK-aware chunking (character-count budgets for Han/Hiragana/Katakana runs vs. word-count budgets for space-delimited scripts) and a low-signal filter that discards symbol-heavy or micro-chunks before a per-chunk majority vote. Default thresholds (`chunk_size=20`, `min_lang_ratio=0.05`) were selected by grid search against a 40-prompt hand-labeled validation set (F1 = 0.76). Full design rationale in [`Language_Detection/README.md`](Language_Detection/README.md).

## Design Principles (repository-wide)

- **Dependency-light.** Outside of `LLM_as_a_Judge` (which necessarily calls an external API) and `Language_Detection` (which uses a small on-device TFLite model), every extractor is pure Python standard library + pandas. No transformer models, embeddings, or GPU inference are required to regenerate the released feature table.
- **Pure, stateless extractors.** Every feature function takes explicit input and returns a flat scalar or dict with no side effects and no shared state — trivially testable and parallelizable via `pandas.apply`.
- **Defensive by default.** `None`, `NaN`, empty strings, malformed metadata, and unexpected types are handled by every extractor with a neutral zero/`False`/`"unknown"` fallback rather than an exception. No row is silently dropped by a missing or malformed field.
- **Column-gated orchestration.** Runners check required input columns before executing a stage — or, for comparison features, before executing each individual comparator — so the pipeline can run against a dataset with only a subset of raw columns present and still produce a valid (if smaller) schema.
- **Non-mutating.** Every runner operates on a copy of its input DataFrame.
- **Provenance-preserving naming.** Column prefixes (`prompt_`, `a_`/`b_`, `dataset_a_`/`dataset_b_`, `cat_`, unprefixed-for-comparisons) always indicate a feature's source and stage, so the origin of any released column is recoverable from its name alone.
- **Label-blind feature engineering.** No module in this repository reads or depends on `winner`. All engineered columns are computable from `user_prompt`, `response_a`, `response_b`, `conv_metadata`, and `category_tag` alone, which is what makes them valid predictors rather than leaked labels.

## Reproducing the Released Feature Table

```python
import pandas as pd
from Feature_Extraction.Feature_Runners.Run_All_Features import run_all_features

df = pd.read_csv("lm_arena_140k.csv")   # raw columns: id, user_prompt, response_a, response_b,
                                          # winner, conv_metadata, category_tag
df = run_all_features(df)
df.to_csv("lm_arena_140k_featurized.csv", index=False)
```

`run_all_features` runs metadata extraction only if `conv_metadata` is present, text extraction only if `user_prompt`/`response_a`/`response_b` are all present, and comparison extraction always — with each comparator individually skipped if its required upstream columns are absent. Stage order (metadata → text → comparison) is fixed, since comparison features consume columns the first two stages produce.

To additionally reproduce the LLM-judge correctness annotations, see the CLI usage in [`LLM_as_a_Judge/README.md`](LLM_as_a_Judge/README.md) — note this step requires an OpenAI API key and incurs API usage cost, and is run and released as a separate artifact from the feature table above.

## Intended Use Cases

- Pairwise LLM preference modeling and reward-model feature engineering, using engineered features as inputs alongside or instead of raw text embeddings.
- Studying **confounds** in human preference judgments — e.g., whether length, formatting richness, or instruction-following complexity predict `winner` independently of actual response quality.
- Response quality and failure-mode analysis (refusals, truncation, near-empty responses) at scale, without per-row manual review.
- Format- and length-compliance auditing: whether a response actually satisfies what the prompt explicitly asked for.
- Cross-referencing engineered structural signals against the independent, non-comparative correctness annotations from `LLM_as_a_Judge` to separate "preferred" from "objectively correct."
- Multilingual and code-switching analysis of prompts and responses via `Language_Detection`.

## Limitations

- Sentence/paragraph segmentation, refusal/truncation detection, and token counts are regex- and heuristic-based, not model-based or tied to a specific tokenizer — they are designed as fast, interpretable proxies, not exact linguistic parses.
- Language and multi-language detection accuracy is bounded by the underlying MediaPipe model and the heuristic cleaning/chunking steps; see [`Language_Detection/README.md`](Language_Detection/README.md) for the validation methodology and its limits (F1 = 0.76 on a 40-prompt validation set).
- `LLM_as_a_Judge` correctness annotations are produced by a third-party LLM API and inherit that model's own error modes; `correctness_applicable=false` intentionally leaves subjective/creative prompts unscored rather than forcing a spurious correctness verdict.
- None of the modules in this repository re-derive or validate the `winner` preference label itself; it is treated as ground truth inherited from the source dataset.
